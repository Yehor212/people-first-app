# Data Model: Android 2.1 Connected Release

> **PRE-RECOVERY DESIGN INVENTORY:** this file describes inherited implementation intent and is not release or migration authority. Reward-related fields are `LEGACY / UNVERIFIED`; public-social/all-ages models require the separately approved S1 sub-spec; remote schema/type parity is currently `FAIL/UNVERIFIED`.

## AutomationPreference

Stored in `db.settings` under one account-synced key. It contains no free-form journal content.

| Field | Type | Invariant |
|---|---|---|
| `schemaVersion` | `1` | Reject unknown major versions |
| `enabled` | boolean | Defaults false; revocation is immediate locally |
| `consentEpoch` | UUID or null | Fresh on each enable; required only for new commits. Revocation nulls the current value but does not prevent owner-authorized undo of retained history |
| `serverRevision` | positive integer | Advanced only by the dedicated preference RPC; generic settings sync cannot write this preference |
| `consentedAt` | safe integer or null | Required when enabled |
| `revokedAt` | safe integer or null | Must be null while enabled. A disabled previously-consented preference records a value >= `consentedAt`; a fresh re-enable rotates the epoch and clears this current-state field while the server audit retains earlier revocations |
| `enabledRuleIds` | rule ID array | Unique, known catalog IDs only |
| `focusHabitId` | string or null | Target must exist, be active, and be explicitly selected |
| `focusMinimumMinutes` | integer | 1..1440 |
| `planningHabitMappings` | map | Habit ID to automation-owned schedule event identity |
| `updatedAt` | safe integer | Monotonic conflict value |

### Dedicated habit planning block

`habit.to-planning.v1` targets the existing `zenflow-schedule-events` account setting, but ownership is evaluated at the mapped event rather than inferred from the whole array. A valid block has the mapped opaque event ID, `source: "habit"`, the exact source `habitId`, `isAutoGenerated: true`, `isEditable: false`, and the same canonical date as the explicit manual completion. The rule changes only `completed` to `true` and sets `completedAt` to the source event's canonical commit timestamp. Missing mappings/blocks, duplicate IDs, manual/editable blocks, another habit/date, resets, skips, auto-filled/legacy entries, and malformed timestamps are typed no-ops.

The full schedule array remains one canonical setting projection so the existing exact before-revision CAS protects concurrent manual edits. Planning preserves array order and every unrelated event field exactly. The first eligible commit may start from a user-owned setting revision because the explicit mapping plus the dedicated non-editable block markers are the event-level ownership transfer; the accepted mutation then records transaction ownership. Undo restores the exact prior array only while the exact after-revision token still matches.

## AutomationTransaction

Stored in a new Dexie table indexed by `id`, `createdAt`, `status`, `ruleId`, and `sourceKey`, and mirrored to an RLS-protected Supabase `automation_transactions` table. The non-encrypted fields must not contain user prose, record titles, habit names, mood notes, or decrypted content.

Locked cross-device deliveries are retained in the v11-only `automationRemoteEvents` store as strict ciphertext-bearing envelopes keyed by immutable sync-event identity. This transient store is account-cleared, excluded from portable backup, bounded to 512 rows per owner, and drained only after a bootstrap marker and current vault are available. Each row is explicitly `delta` or `snapshot`: deltas remain contiguous and may apply domain mutations, while sparse snapshot rows authenticate and restore retained ledger metadata without replaying over the already-fetched current domain snapshot. It preserves multiple server states for one transaction (for example commit sequence 100 followed by undo 101) until replay can apply them atomically in authoritative order.

| Field | Type | Invariant |
|---|---|---|
| `id` | UUID | Stable across retries/devices |
| `ownerUserId` | UUID | Must equal durable/session owner; cloud owner is derived from `auth.uid()` |
| `consentEpoch` | UUID | Historical enable epoch; must equal current enabled preference for commit, but remains valid evidence for later undo |
| `sourceKey` | SHA-256 identity | Recomputed from owner, source type/id/revision, rule/version and consent epoch |
| `ruleId` / `ruleVersion` | known string / integer | Catalog entry must exist |
| `sourceType` | enum | `mood`, `journal`, `focus`, `habit` |
| `sourceId` | string | Opaque domain ID; never logged with user text |
| `status` | enum | `commit_pending`, `committed`, `sync_blocked`, `commit_conflict`, `revoked`, `undo_pending`, `undone`, `conflict` |
| `revisionCiphertext` | string | Valid authenticated automation envelope; never plaintext |
| `createdAt` / `updatedAt` | safe integer | Monotonic; server order resolves equal-device races |
| `undoneAt` | safe integer optional | Present only when undone |
| `undoTransactionId` | UUID optional | Links compensating transaction |
| `serverSequence` | positive integer optional | Absent until server accept; authoritative replay order afterward |
| `historyGeneration` | positive integer optional | Must equal current owner generation; stale generations never import/replay |
| `schemaVersion` | `1` | Boundary validation required |

## AutomationSourceIntent (local only)

Stored in the same v11 table as a discriminated `source_pending` row. It contains only `ownerUserId`, exact `consentEpoch`, captured `OriginAccountBoundaryGeneration`, source type/opaque ID/revision, rule-catalog candidate, stable `sourceKey`, and timestamps—never mood notes, journal text, habit names, titles, or a domain snapshot. The primary domain adapter writes this intent and the user-authored source record in one Dexie transaction. The coordinator later revalidates the exact epoch/generation and claims it idempotently; E1→revoke→E2 or owner-boundary changes discard the intent while retaining the primary record. Sign-out, account switch, deletion barriers, and v11-aware clear include these rows.

## AutomationRevisionEnvelope (encrypted)

Encrypted with the current account-recoverable journal vault key using fresh salt/IV and authenticated AES-GCM. Canonical JSON is used before encryption and hashing.

| Field | Type | Invariant |
|---|---|---|
| `schemaVersion` | `1` | Required |
| `transactionId` | UUID | Matches outer row |
| `ownerUserId` | UUID | Must match durable local/session owner at decrypt/apply time |
| `source` | object | Validated source snapshot and revision identity |
| `mutations` | array | 1..32 exact target mutations |
| `plannedAt` | safe integer | Clock seam in tests |

Each mutation has `entityType`, `entityId`, operation (`upsert` or automation-owned `delete` for undo only), canonical `before`/`after` values, SHA-256 hashes, `beforeRevisionToken`/`afterRevisionToken`, and a normalized ordered-event intent. Null is allowed only for an absent state. The commit RPC compares all planned-before tokens/absence before writing; undo compares exact after tokens. Value/hash equality never substitutes for the token.

## Automation provenance on derived records

An optional `automation` object is added through passthrough-compatible domain schemas:

```text
schemaVersion, ownerUserId, transactionId, consentEpoch, sourceKey,
ruleId, ruleVersion, sourceType, sourceId, recordRevisionToken,
mutationGeneration, afterHash, createdAt
```

This object contains no source text. Every manual edit rotates the record revision and detaches automation ownership even if the value later returns to the same hash. This makes A→B→A an undo conflict instead of a false match.

## StorageIncidentSignal (ephemeral UI/runtime evidence)

This signal is not user history and is never synchronized, backed up, exported, or used as proof that recovery data exists. One active signal per stable incident key is retained only in component state; a repeated signal replaces rather than stacks with the same key.

| Field | Type | Invariant |
|---|---|---|
| `code` | fixed enum | Examples are bounded storage timeout/open-blocked/operation-failed categories; never raw exception text |
| `phase` | fixed enum | `open`, `upgrade`, `read`, `write`, `transaction`, or `unknown`; never a table name, key, owner ID or record value |
| `deadlineMs` | bounded positive integer optional | Diagnostic context only; changing it is not a remediation |
| `recoveryState` | `cached`, `unavailable`, or `unknown` | `cached` is legal only after a validated domain recovery snapshot was actually read |
| `retryable` | boolean | True only when the caller supplies an idempotent, owner-safe retry path |
| `occurredAt` | safe integer | Local ordering/dedup only; not analytics or synchronized evidence |

The localized title, message and retry label are selected from `code`, `phase`, and `recoveryState`; callers cannot inject free-form prose. Low-priority signals use polite status semantics without focus movement. Critical persistence/sign-out incidents may use assertive alert semantics but remain dismissible/recoverable and cannot cover the current focused or primary action.

## State transitions

```text
primary record + source_pending -> derived local commit -> commit_pending
commit_pending + server CAS accept -> committed
commit_pending + retry exhaustion -> sync_blocked -> committed after retry
commit_pending + stale before-token -> local token-safe compensation -> commit_conflict
commit_pending + stale consent epoch -> local token-safe compensation -> revoked
committed + undo request -> undo_pending (zero domain mutation)
undo_pending + accepted server CAS -> undone; duplicate request returns canonical undone
undo_pending + newer server target state -> conflict
conflict + no manual resolution -> conflict (no automatic overwrite)
```

Duplicate `(ownerUserId, sourceKey)` returns the canonical row. `undone` and `revoked` are terminal for the original transaction; reapplying the source requires a new source revision and current epoch, not status reuse. The server rejects a new commit whose epoch no longer matches the currently enabled preference, but historical undo does not require automation to remain enabled.

## Server-atomic batch contract

- The client persists exactly one stable-ID `COMMIT_AUTOMATION_TRANSACTION` offline action in the same Dexie transaction as derived rows and the local ledger row.
- The commit RPC validates `(select auth.uid())`, current preference epoch, the typed outer schema, ciphertext prefix/size, recomputed source-key uniqueness, device ID, and bounded projections for only journal entries, moods, habit completions, and account settings schedule values. It compare-and-sets every planned-before revision/absence before any write; deterministic create collisions are accepted only as the exact same canonical transaction.
- In one PostgreSQL transaction it applies every supported canonical domain projection, inserts/upserts the owner ledger row, records any required permanent top-level tombstone, and inserts one immutable `sync_events` row with `entity_type = 'automation_transaction'` and ciphertext payload. There is no later independent materialization step.
- The undo RPC validates ownership plus transaction/provenance identity and compares every current domain projection's exact after-revision token before any write. A mismatch rejects the entire CAS even when values/hashes match. A duplicate request for an already-undone transaction returns its canonical result. Only an accepted CAS restores prior projections or deletes automation-created records and emits permanent tombstones plus one compensating ledger/event.
- The RPCs never accept arbitrary table names, SQL fragments, service-role credentials, unsupported entity types, or decrypted revision prose in the ledger/event. Typed domain projections carry only the values already governed by each canonical sync contract.
- The server assigns each accepted ledger row an owner-scoped monotonic `serverSequence` and current `historyGeneration`. A remote client applies decrypted mutations in one Dexie transaction. A locked client stores rows and reconciles strictly by server sequence after vault unlock, regardless of delivery order.
- On the first 2.1 owner hydration and N-1 upgrade, one typed snapshot RPC is called through bounded keyset pages containing at most 128 rows from each of the transaction, tombstone, and record-revision streams (384 rows total). Every page is bound to the same `(historyGeneration, snapshotSequence, recordRevisionVersion)` token; a concurrent transaction, purge, or manual target edit returns `SNAPSHOT_STALE`, discards the accumulator, and restarts. There is no lifetime tombstone/revision count ceiling and no offset pagination. Only after the final page does the client atomically verify every local projection hash, adopt exact server revision tokens, reject stale generations/tombstoned IDs, and retain locked ciphertext independently of the existing event cursor. Sparse snapshot rows authenticate in server order without requiring deleted historical sequence numbers; only subsequent delta rows require contiguous order.
- A locked marker may have `snapshotSequence > lastAppliedServerSequence`: accepting the snapshot and authenticating its ciphertext are separate durable phases. Once all snapshot rows authenticate after unlock, the client advances directly to the snapshot boundary and resumes contiguous deltas. No client timestamp may fill or reorder a server-sequence gap.

## Account and deletion behavior

- Sign-out/account switch clears local automation rows and pending outbox alongside other account data.
- Cross-device transaction history is recovered from the owner ledger independently of ordered-event retention/cursor state after account ownership is established.
- Account deletion uses existing terminal barriers; automation outbox cannot upload after deletion begins.
- User-created records are never automatically deleted. Undo may delete an automation-created record only when its current hash/provenance still matches.
- The user may vault-authorize forgetting one transaction or all connected history. A per-item purge records the transaction ID in an owner tombstone set; all-history purge advances the owner `historyGeneration` and returns the exact server-disabled preference. The server commits marker/tombstones before any local ciphertext or outbox row is removed. Local record-revision tokens are detached from forgotten transaction/undo IDs but may remain as prose-free CAS metadata; they do not depend on the journal vault and cannot block password removal. The action explicitly and permanently removes undo; old-generation or tombstoned event/backup/outbox replay is rejected, including a delayed pre-purge success response.
- Diary password removal is blocked while encrypted history exists. The user may cancel password removal and leave automation paused indefinitely without deleting history. If the user separately chooses all-history purge, it disables automation and must complete cross-device deletion before journal protection removal can continue.

## Authenticated binding

The encryption associated data (or an equivalently authenticated wrapper) binds `schemaVersion`, `ownerUserId`, `transactionId`, `sourceKey`, `ruleId` and `ruleVersion`. Decrypt/apply compares every bound value with the outer row before exposing mutations. Same-owner import retains the binding; cross-owner import is rejected instead of copying opaque ciphertext into another account.

## SocialInviteEnvelope (untrusted transport only)

Friend and challenge invitations use separate versioned schemas. The envelope is never a friend/challenge record and decode never writes local or cloud state.

| Field | Type | Invariant |
|---|---|---|
| `version` | `1` | Unknown versions fail closed |
| `type` | `friend` or `challenge` | Caller must request the same type; cross-type redemption fails |
| `origin` | fixed allowlisted HTTPS origin | No arbitrary host, scheme, path traversal or redirect |
| `code` | bounded opaque string | Contains no auth token, raw user ID, profile field, habit/journal/mood data or embedded challenge facts |

`friend.v1` and `challenge.v1` remain distinct even if their opaque codes share an alphabet. The resolver derives the owner from the authenticated session and enforces RLS, expiry, revocation, self/duplicate membership, blocking/removal, rate limits and challenge availability. Its preview returns only the minimum canonical display fields required for the decision and an opaque redemption revision; explicit Add/Join submits that revision in a compare-and-set request. Offline or unresolved input persists nothing.

QR and manual input carry the same HTTPS envelope and call the same parser/resolver. A static QR is accompanied by selectable code, Copy and Share. Scanner cancellation/denial/backgrounding is terminal for that scan only. No camera image, barcode frame or decoded payload is stored in analytics, logs, backups or diagnostics.

## AdAvailabilityEvidence (redacted operational evidence)

One row records each layer independently: authenticated account/app/unit status, UMP message assignment, `app-ads.txt` crawl, candidate release configuration, deployed authenticated service-gate revision/freshness, consent/controller state, SDK request category and fill/no-fill result. Values are fixed/bounded and exclude credentials, raw ad responses, user/ad identifiers and personal state. A later layer cannot override an earlier `FAIL`; a test-device result cannot become live-production serving proof.

## Backup and import

- Backup schema increments to include encrypted automation rows and the history deletion marker without decrypting portable backup content.
- Import validates metadata/envelope shape, preserves ciphertext, owner-binds writes, and merges by `updatedAt`/server order.
- Import requires current marker snapshot, rejects lower `historyGeneration` or per-item tombstoned IDs, and orders accepted rows by `serverSequence`; client timestamps cannot outrank server order.
- A replace import requires the existing journal replacement authorization because encrypted history can restore or remove personal records.
- Old backup schemas remain readable and produce an empty automation collection.

## Forward-only compatibility

Dexie can open a database created by a newer schema without teaching an old binary about the extra object store. Therefore a v10 binary cannot guarantee account-bound deletion of v11 automation rows. The release requires a compatibility RED test and a forward-only operational rule: after v11 distribution, every rollback/hotfix artifact must include v11-aware clearing and migration code.

## Limits

- Maximum 32 mutations per transaction.
- Maximum 90,000 characters per encrypted transaction envelope; larger plans fail closed and remain manual.
- Maximum 128 retained history rows and 8 MiB cumulative ciphertext per owner. Reaching either limit pauses new automatic writes and leaves the primary action unaffected. The user may remain paused indefinitely; clearing history is an optional, separately authorized destructive action. Version 2.1 performs no silent truncation, pruning, compaction, or pressure to clear.
- Portable backup serialization still enforces the existing 32 MiB whole-file limit. It fails with the existing explicit capacity error if all content cannot fit; it never drops history rows to make an export appear successful.
- All timestamps must be finite safe integers; all dates use canonical `YYYY-MM-DD` helpers.
